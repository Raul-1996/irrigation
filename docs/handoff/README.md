## 4. Что осталось сделать

Три очереди, в порядке приоритета.

### Очередь 1 — верифицировать 113 непроверенных находок
Это самое важное и самое дешёвое действие. Находки формулировались агентами-искателями
и **не проходили проверку** — среди них заведомо есть ложные (в проверенной выборке
опровергался примерно каждый четвёртый). Чинить их без верификации нельзя.

Промт верификатора — в `agent-prompts.md`, раздел B. Группировать по областям
(планировщик, zone_control, db, mqtt, frontend, безопасность, тесты).

### Очередь 2 — исправить подтверждённое
19 подтверждённых находок; после дедупликации это 8 независимых дефектов.
Разбивка на батчи с промтами — `agent-prompts.md`, раздел C.

Самый серьёзный: **`db/programs.py:64` — сдвиг дней недели на −1**. Эвристика
«легаси 1-индексации» срабатывает для любого набора дней без понедельника, поэтому
программа «Вт+Ср» сохраняется как «Пн+Вт» и поливает на день раньше. Каждое повторное
сохранение сдвигает ещё раз. Баг живой, есть и на `main`, требует ещё и миграции
уже испорченных строк — но миграция не может отличить «испорченное» от «правильного»,
так что нужно решение владельца (см. раздел 6).

### Очередь 3 — отложенный структурный рефакторинг
Сознательно не делалось как самое рискованное:
- `irrigation_scheduler.py` (2 358 строк) — два почти одинаковых 400-строчных секвенсора зон;
- `static/js/status.js` (~2 400 строк) — 10+ ответственностей в одном файле.

Фундамент под это уже подготовлен: мёртвые дубли удалены, реестр джобов един,
расчёт следующего полива вынесен в сервис.

## 5. Правила работы с этим репозиторием

- **Python 3.11 минимум**, фичи 3.12+ запрещены (`tomllib`, `asyncio.TaskGroup`,
  `except*`, generic syntax). PEP 604 (`X | None`) — можно. Причина: на контроллере
  Wirenboard системный python3.9, приложение живёт в отдельном venv с 3.11 через `uv`.
- **Локальное окружение:** `uv venv --python 3.11 .venv && uv pip install -r requirements.txt -r requirements-dev.txt`.
- **Тесты:** `.venv/bin/python -m pytest -q` — должно быть `1872 passed, 2 skipped, 17 deselected`.
  e2e и mqtt_real деселектятся по умолчанию; включаются через env-переменные.
- **Параллельный прогон (`-n 4`) флейкает** на логин-тестах — судить всегда по серийному.
- **Линтер:** `uvx ruff check .` (конфиг в `pyproject.toml`, target py311).
- **Прод — Wirenboard, один процесс:** hypercorn + фоновые треды (APScheduler, paho,
  watchdog). Любые локи и блокирующие вызовы под ними — потенциальный дедлок всего
  приложения; в этой ветке один такой уже был найден и исправлен.
- **Коммиты:** осмысленные, по одному логическому изменению; после каждого — прогон
  тестов; пушить на `origin` (пользователь просил не держать работу только локально).

## 6. Что НЕ трогать без решения владельца

- **Коэффициент водного баланса H2** не подключён к реальному поливу — это намеренный
  shadow-режим (флаг выключен), а не забытый код.
- **Миграция уже сдвинутых дней недели** (см. очередь 2): в БД нельзя отличить
  строку, испорченную эвристикой, от корректной. Варианты: (а) чинить только код и
  попросить пользователя перепроверить расписания в UI; (б) одноразовая миграция
  с допущением, что все существующие программы сдвинуты. Нужно решение владельца.
- **Служебная группа 999** («БЕЗ ПОЛИВА») — специальная семантика, исключается из
  отчётов; сравнивать строго `== 999` (был баг с `>= 999`, исправлен).

## 7. Как продолжить на другой модели

1. Прочитать этот файл и `findings-inventory.md` (раздел UNVERIFIED — самый большой).
2. Взять промт верификатора из `agent-prompts.md` (раздел B), прогнать по областям.
   Верификатор обязан проверять код сам и по умолчанию опровергать при сомнении —
   это единственное, что удерживает поток находок от превращения в поток ложных правок.
3. Подтверждённое чинить батчами из раздела C, каждый батч: правка → регрессионный
   тест → полный прогон → коммит → push.
4. Не начинать очередь 3, пока не закрыты 1 и 2.
