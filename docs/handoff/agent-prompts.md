### FIX-1 (high, прод-баг) — сдвиг дней недели на −1

```
[раздел A + общее правило]

Файл: db/programs.py, строки ~64 (create_program) и ~114 (update_program), плюс
duplicate_program (~174).

Проблема: эвристика «легаси 1-индексации»
    if norm_days and min(norm_days) >= 1 and max(norm_days) <= 7:
        norm_days = [max(0, min(6, d - 1)) for d in norm_days]
срабатывает для ЛЮБОГО набора дней, не содержащего 0 (понедельник), потому что
фронтенд шлёт 0-6 и условие max <= 7 истинно всегда. В результате программа
«Вт+Ср» (days=[1,2]) сохраняется как [0,1] и поливает в Пн+Вт — на день раньше.
Каждое повторное сохранение сдвигает ещё раз ([5,6] → [4,5] → [3,4]).
duplicate_program прогоняет сохранённые дни через create_program и сдвигает копию.

Проверено выполнением: create_program(days=[1,2]) сохраняет [0,1].
Единственный клиент API — templates/programs.html — шлёт 0-индексированные дни
(0=Пн; кнопка «Будни» = [0..4], «Выходные» = [5,6]). Планировщик трактует хранимые
дни как 0=Пн (CronTrigger day_of_week, now.weekday()). То есть 1-индексированных
клиентов в природе нет, и эвристика вредна целиком.

Задача:
1. Удалить эвристику из create_program, update_program и любых других мест
   (сначала grep по репозиторию: возможно, она продублирована).
2. Оставить нормализацию, которая реально нужна: приведение к int, отсечение
   значений вне 0..6, дедупликация, сортировка.
3. Регрессионные тесты: days=[1,2] сохраняется как [1,2]; повторный update не
   меняет значения; duplicate_program сохраняет дни оригинала; days=[0..6] и
   пустой список работают как раньше.
4. НЕ писать миграцию данных: отличить уже испорченную строку от корректной
   невозможно. Вместо этого добавь в docs/handoff/README.md пункт для владельца:
   после деплоя проверить расписания программ в UI.
```

### FIX-2 (high) — SSE-хаб сбрасывает таймер автостопа по эху реле

```
[раздел A + общее правило]

Файл: services/sse_hub.py, ~строки 263-269 (_on_message).

Проблема: на любое наблюдаемое значение 'on' по топику зоны безусловно выполняется
    sched.cancel_zone_jobs(zid)          # удаляет и zone_stop:*, и zone_hard_stop
    sched.schedule_zone_stop(zid, dur)   # dur = БАЗОВАЯ длительность зоны из БД
Hard-stop обратно не планируется. Обработчик не отличает эхо собственной команды
старта от внешнего включения реле.

Два подтверждённых сценария:
(1) Старт с override-длительностью: override-стоп и hard-stop планируются ПОСЛЕ
    возврата exclusive_start_zone, а эхо может обработаться раньше — тогда полив
    на 2 минуты превращается в полив на базовые 30.
(2) Детерминированный: retain '1' висит на топике весь полив; при реконнекте к
    брокеру (рестарт mosquitto, блип сети, reload_hub при редактировании зоны)
    _on_connect ресабскрайбится, брокер доставляет retained '1' → таймер стопа
    сбрасывается на ПОЛНУЮ базовую длительность от текущего момента, hard-stop
    удаляется навсегда. Остаётся только cap-watchdog на 240 минут.

Задача: перепланировать автостоп только тогда, когда его действительно нет
(зона включилась внешней командой, а не нашей). Варианты, выбрать обоснованно:
- планировать стоп только если для зоны НЕТ активных zone_stop/zone_hard_stop джобов;
- либо сверять с planned_end_time зоны и не трогать таймер, если он в будущем;
- либо помечать собственные команды (command_id) и игнорировать эхо своих.
В любом случае hard-stop, если он был снят, должен восстанавливаться.

Тесты: эхо 'on' при живом override-стопе не меняет planned_end_time и не удаляет
джобы; эхо 'on' для зоны без активных стоп-джобов планирует стоп на базовую
длительность (текущее полезное поведение сохраняется).
```

### FIX-3 (medium, привнесено веткой) — reload_hub блокирует SSE под локом

```
[раздел A + общее правило]

Файл: services/sse_hub.py, reload_hub (~строка 402) → ensure_hub_started (~430).

Проблема: reload_hub вызывается из HTTP-обработчиков (routes/zones_crud_api.py:137,

- либо строить новые клиенты вне лока, а под локом только атомарно подменять реестр.
Дедлок, уже исправленный ранее в этой функции (loop_stop под локом), не должен
вернуться: обрати внимание, что _on_message берёт тот же лок.

Тест: reload_hub при недоступном брокере не блокирует broadcast дольше, чем на
доли секунды (мокнуть connect с задержкой и проверить, что broadcast проходит).
```
